# План реализации тематического чата

**Оценка: 13–18 рабочих часов на MVP и сдачу.** Это оценка работы, а не расписание: в неё входят тесты и один проход ревью на задачу; ожидание внешнего доступа, CI и повторные циклы ревью считаются отдельно. Цель — одна проверяемая задача на ветку, примерно 1–2 часа.

## Что сохраняем из согласованной архитектуры

- FastAPI и `src/`-layout, HTML/CSS/JS без фреймворка, явная сборка зависимостей в `create_app()`. Сценарий чата зависит от интерфейсов хранилища и генератора, не от SQLAlchemy или Gemini.
- `uv` — единственный менеджер проекта и зависимостей: фиксируем версию Python, `pyproject.toml` и `uv.lock`; тестовые инструменты — в группе `dev`. Локально и в CI устанавливаем зависимости через `uv sync --locked`; в образе — без `dev`. `uv lock --check` проверяет актуальность lock-файла, не обновляя его ([uv: Locking and syncing](https://docs.astral.sh/uv/concepts/projects/sync/)).
- YAML для модели, системного промпта и незасекреченных настроек БД; локальный `.env` для ключа доступа, секрета подписи cookie, ключа Gemini и DSN PostgreSQL с паролем. Секреты не попадают в YAML, Git, образ или логи. Конфиг валидируется при старте; окружение имеет приоритет над соответствующим файлом.
- Один общий чат, как в исходном плане. В LLM отправляются только системная инструкция и текущее сообщение; история для интерфейса не участвует в генерации. Генерация и запись происходят последовательно внутри одного запроса: сначала ответ модели, потом короткая транзакция, потом HTTP-ответ. Два гостя могут отправить запросы одновременно: готовые ходы сохраняются целиком и читаются по серверному ID хода, без обещания порядка прихода HTTP-запросов. При таймауте ход не сохраняется, черновик остаётся у отправителя.
- **Нужно различить два требования к I/O.** Рекомендуемый вариант — асинхронные драйверы БД и Gemini через `async/await`, но последовательные шаги запроса, без фоновых задач. Если буквально требуются синхронные клиенты БД и модели, используем sync-драйверы и синхронные HTTP-обработчики, не вызываем блокирующие клиенты напрямую из `async def`. Каркас и типизированные настройки можно делать до выбора; реализацию интерфейсов I/O начинаем после него.

## Пользовательские ID и ручки

Не передаём `user_id` как параметр, определяющий от чьего имени делать запрос. После проверки общего ключа middleware обработчик входа создаёт гостя с серверным UUID (или повторно использует ID из действующей сессии). Cookie выдаётся только после сохранения гостя. Middleware проверяет подписанную cookie на закрытых ручках, сервер берёт ID автора из неё. Это соответствует рекомендации [OWASP: IDOR Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Insecure_Direct_Object_Reference_Prevention_Cheat_Sheet.html) определять текущего пользователя по сессии, а не по полю запроса.

- `users(id UUID, created_at)`: идентификатор гостя, не учётная запись. Ключи и другие личные данные в таблицу не записываются.
- `chat_turns.user_id` — обязательный внешний ключ к `users.id`, обозначает автора вопроса. Автор ответа — модель; отдельный пользователь для неё не создаётся.
- `POST /api/session` принимает ключ и устанавливает cookie. `GET /api/messages` возвращает **общую** историю. `POST /api/messages` принимает только `{ "text": "…" }`, посторонние поля отклоняются. Если нужно пометить в UI «Вы», сервер может вернуть `is_mine`, не раскрывая UUID всех участников.
- Обновление страницы и перезапуск с тем же секретом подписи не меняют действующую сессию. Другой браузер, удалённая или истёкшая cookie после нового входа означают нового гостя. Общая история сохраняется. Общий ключ не позволяет надёжно узнать одного человека на разных устройствах; личную историю не обещаем без отдельной учётной записи или индивидуального ключа.

| 5 | `agent/feat/chat-api` | 1,5–2 | Сценарий чата и HTTP-контракт: пределы текста, общий диалог, автор из сессии, корректная ошибка модели. Сквозной тест с внедрёнными подменами; подмена модели никогда не используется как fallback реального режима. |

| 8 | `agent/feat/chat-ui` | 1,5–2 | Вход и чат в одном документе, счётчик, блокировка отправки, сохранение черновика при ошибке, загрузка истории и отображение текста без интерпретации как HTML. |

Порядок — от свежего `main`, без зависимых PR в очереди: следующий срез стартует после слияния предыдущего, если затрагивает его интерфейсы. Если задача перестаёт помещаться в 2 часа, отделяем часть с собственным критерием приёмки, а не раздуваем PR.

## Условие слияния

1. **Нулевой Git-шаг и issue.** В оценку первого среза входит подготовка базы: в новом пустом репозитории проверяем Git identity, заводим локальный реестр, подключаем проектные хуки и делаем один минимальный начальный коммит в `main`. Весь рабочий код — в ветках от `main`. До работы фиксируем критерий приёмки в issue. Без remote ревью и гейты привязываем к SHA локальной ветки; это не GitHub PR.
2. **RED → GREEN → рефакторинг.** На новое поведение сначала запускаем тест и убеждаемся, что он падает по ожидаемой причине. После реализации запускаем весь набор. Коммиты небольшие, по делу: `feat(auth): …`, `fix(chat): …`, `refactor(storage): …`, `test(...)`, `ci(...)` или `docs(...)`. В заголовке — номер реального issue, в теле — краткое описание изменений.
3. **Независимое adversarial review.** Отдельному саб-агенту передаём критерии и точный diff от актуального `main`: он ищет регрессии и пробелы в тестах, а не подтверждает описание автора. Для сессий — закрытые маршруты, подмена идентичности, expiry и утечки; для БД — миграции, целостность и персистентность; для UI — повторная отправка и обработка ошибок. При существенных замечаниях исправляем и повторно проверяем финальный diff.
4. **Гейты.** `uv lock --check`, `uv run --locked ruff check .`, `uv run --locked ruff format --check .`, `uv run --locked pytest`, проверка документации; профиль PostgreSQL и smoke-сценарий добавляются по мере готовности. На GitHub мержим PR только после зелёных проверок на актуальном коммите и закрытых существенных замечаний ([GitHub Docs: Status checks](https://docs.github.com/en/pull-requests/reference/status-checks)). Ревью саб-агента фиксируем в описании PR; оно не подменяет формальное approval, если его требует политика репозитория.

На момент составления плана рабочая папка не является Git-репозиторием; GitHub-адрес не задан. Пока remote отсутствует, ветки и проверки возможны локально, но GitHub PR/Actions и опубликованный `main` — нет. Перед публикацией нужно сопоставить локальные issue ID с реальными номерами GitHub, а не выдавать одно за другое.
