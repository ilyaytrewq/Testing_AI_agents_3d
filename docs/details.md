## Запуск без Docker

Нужны [uv](https://docs.astral.sh/uv/) и PostgreSQL с уже созданными базой и ролью. После `make env` добавьте в `.env` строки `LLM_API_KEY=...` и `DATABASE_URL=postgresql+asyncpg://user:password@127.0.0.1:5432/themed_chat?ssl=disable`, затем:

```sh
uv sync --locked
uv run --locked uvicorn themed_chat.app:create_app --factory --port 8000
```

Миграции применяются при старте.

## Конфигурация

- [config/app.yaml](../config/app.yaml) — настройки по умолчанию. Путь к файлу можно сменить через `APP_CONFIG_FILE`. В Compose каталог `config/` подключён к контейнеру только для чтения: после правки промпта или темы достаточно `docker compose -f compose.local.yaml restart chat`, пересборка не нужна.
- Любое значение YAML переопределяется переменной `APP_<СЕКЦИЯ>__<ПОЛЕ>`, например `APP_LLM__MODEL` или `APP_AUTH__LOGIN_ATTEMPTS`.
- [.env.example](../.env.example) — шаблон секретов. В Compose `DATABASE_URL` собирается в [compose.local.yaml](../compose.local.yaml) из `POSTGRES_PASSWORD`, поэтому пароль должен быть URL-безопасным (hex из `make env` подходит). Порт БД наружу не публикуется, история лежит на томе `postgres-data`.
- Порт на хосте: `CHAT_PORT=8080 docker compose -f compose.local.yaml up --build -d --wait`.

| Ключ | По умолчанию | Назначение |

## Смена модели

Провайдер выбирается в `llm.provider` (по умолчанию `openai_compatible`, другого пока нет); неизвестное имя — ошибка конфигурации при старте. Новый провайдер — это один модуль в `src/themed_chat/adapters/` с функцией подключения, которая отдаёт объект с методами `generate` и `complete` (порт `ModelClient`), и одна строка в словаре `PROVIDERS` в [adapters/providers.py](../src/themed_chat/adapters/providers.py).

По умолчанию используется Google Gemini через его OpenAI-совместимый API. Подойдёт любой сервис с таким API: укажите базовый URL и ID модели, а в `LLM_API_KEY` — ключ этого сервиса. В Compose это три переменные в `.env`:

```dotenv
APP_LLM__BASE_URL=https://generativelanguage.googleapis.com/v1beta/openai/
APP_LLM__MODEL=gemini-3.8-flash
LLM_API_KEY=ключ-сервиса
```

Не дописывайте `/chat/completions`: клиент добавляет путь сам. API должен принимать Bearer-ключ и сообщения с ролями `system` и `user`, а в ответе возвращать строку в `choices[0].message.content`. Ключ отправляется на настроенный адрес, поэтому меняйте его вместе с URL. `llm.base_url` должен быть HTTPS; обычный HTTP допустим только для loopback (`127.0.0.1`, `localhost`, `[::1]`). Прокси из переменных окружения (`HTTPS_PROXY` и др.) клиент не использует, редиректы не выполняет. Сервер на хосте Docker Desktop недоступен из контейнера по loopback, поэтому для него нужен HTTPS-адрес, доступный из контейнера (например, `https://host.docker.internal:…`). После правки `.env` выполните `docker compose -f compose.local.yaml up -d --wait`.

## Авторизация: подробности

- **Проверка ключа.** Сначала формат (8–255 символов: латинские буквы, цифры, `-`, `_`), затем сравнение с эталоном за постоянное время: сравниваются HMAC-SHA256-дайджесты одинаковой длины через `hmac.compare_digest`, поэтому по времени ответа нельзя узнать длину ключа.
- **Сессия.** Запись в таблице `sessions`: случайный id, гость, отпечаток ключа, срок `session_ttl_seconds`. Каждый запрос к API проверяет, что запись есть, не отозвана, не истекла и её отпечаток совпадает с текущим ключом (одно чтение из БД). Истёкшие записи удаляются при следующих входах. Повторный вход заменяет прежнюю сессию, удаление гостя удаляет и его сессии.
- **Отпечаток.** HMAC-SHA256 ключа, посчитанный секретом подписи (`APP_SESSION_SECRET`). Если `APP_ACCESS_KEY` изменился, старые сессии не совпадают с отпечатком и перестают работать.
- **Origin.** Для loopback-адреса (`127.0.0.1`, `localhost`, `[::1]`) годится любое из этих имён при той же схеме и порту; для остальных адресов нужно точное совпадение с `auth.public_origin` (в Helm — `publicOrigin`).
- **Гость.** Каждый успешный вход без cookie `chat_guest` создаёт в БД нового гостя. Эта долгоживущая подписанная cookie (`HttpOnly`, `SameSite=Lax`, `path=/api`, около года) нужна только для подписей «Вы» и «Гость» и ничего не разрешает: доступ даёт лишь сессия.
- **Лимиты.** Вход: после превышения `429` с заголовком `Retry-After`. Число отслеживаемых адресов и гостей ограничено, при переполнении самые старые записи вытесняются. Счётчики хранятся в памяти одного процесса.
- **Прокси.** За прокси задайте `auth.trusted_proxies` (список CIDR): только если TCP-соединение пришло из этих сетей, адресом клиента считается самый правый адрес в `X-Forwarded-For`, который сам не входит в доверенные. Иначе заголовок игнорируется, так что клиент не может подставить чужой адрес. Этот адрес используют лимит входа и логи. Без настройки за прокси все пользователи делят один лимит.
- **Секреты.** Для каждого секрета (`APP_ACCESS_KEY`, `APP_SESSION_SECRET`, `LLM_API_KEY`, `CLASSIFIER_API_KEY`, `DATABASE_URL`) можно вместо `NAME` задать `NAME_FILE` с путём к файлу; один завершающий перевод строки отбрасывается, а `NAME` и `NAME_FILE` одновременно — ошибка конфигурации. Ключ доступа и секрет подписи должны различаться, приложение иначе не запустится. `make env` не перезаписывает существующий `.env`, создаёт его с правами `0600` и тремя разными случайными значениями: `APP_ACCESS_KEY`, `APP_SESSION_SECRET`, `POSTGRES_PASSWORD`.

## Защита темы: подробности

Защита включена по умолчанию (секция `guard` в [config/app.yaml](../config/app.yaml)). Детерминированного фильтра ответа нет: обе проверки делает классификатор-LLM.

**Классификатор вопроса.** Отдельный короткий вызов LLM со своим промптом возвращает метку `ON_TOPIC` или `OFF_TOPIC` и язык вопроса (код ISO 639-1). По умолчанию (`guard.structured_output: true`) запрос просит структурированный ответ через `response_format` с JSON-схемой `verdict` (`strict`), и ответ разбирается строго как объект `{"label": ..., "lang": ...}`. Для провайдеров без поддержки `json_schema` задайте `guard.structured_output: false` (`APP_GUARD__STRUCTURED_OUTPUT=false`): тогда классификатор отвечает текстом `ON_TOPIC ru`; кавычки или обратные апострофы вокруг, точка в конце, язык в верхнем регистре и перевод строки между меткой и языком допускаются, сама метка — нет.

Вопрос не по теме, в том числе о модели, промпте, ключах и устройстве сервиса, получает фиксированный отказ на языке вопроса из `guard.refusals` (не меньше ru, en, de, uk, zh, es, fr; для других языков — `guard.default_refusal_language`). Основная модель при этом не вызывается, отказ сохраняется в историю как обычный ответ. Соседние темы (молоко, сиропы, десерты к кофе, кофеин, чай в сравнении с кофе) допустимы только как короткое упоминание в ответе о кофе или как вопрос о кофе; полный рецепт десерта, медицинские советы и заваривание чая — не по теме.

**Защитный промпт.** Вопрос уходит основной модели внутри `<user_question>…</user_question>` как данные; закрывающий тег внутри вопроса обезвреживается.

**Проверка ответа.** Тот же классификатор со своим промптом проверяет ответ основной модели: код в любом виде, упоминание моделей и провайдеров ИИ на любом языке, пересказ инструкций, похожие на ключи строки, рассказ об устройстве сервиса или уход от темы дают `OFF_TOPIC`, и ответ заменяется отказом на языке вопроса.

**Нет вердикта.** Если классификатор ответил, но вердикта в ответе нет (пустой или обрезанный ответ, не тот формат, неизвестная метка), вопрос считается не по теме: отказ на языке `guard.default_refusal_language` для вопроса и на языке вопроса для ответа, основная модель не вызывается, в лог пишется ошибка без текста. В режиме структурированного ответа BOM и обёртка ```` ``` ````/```` ```json ```` снимаются, дублирующиеся ключи не принимаются, а если JSON не разобрался, пробуется текстовый вердикт `ON_TOPIC ru`.

**Сбой провайдера.** Если вердикта нет `guard.no_verdict_outage_threshold` раз подряд (по умолчанию 3; счётчики отдельные для проверки вопроса и проверки ответа, общие для всех запросов процесса, и каждый сбрасывается только настоящим вердиктом на своём этапе), это считается сбоем: пользователь получает `502`, вопрос сохраняется как неотвеченный. Так провайдер, который перестал соблюдать формат, не превращает чат в поток отказов незаметно. Если классификатор не ответил за `guard.classifier_timeout_seconds` (10 с) или провайдер вернул ошибку, пользователь получает `504`/`502`, а вопрос сохраняется как неотвеченный: сбой провайдера не выглядит как отказ, и ответа в обход проверки нет.

**Цена.** До двух дополнительных вызовов LLM на сообщение, поэтому ответ медленнее и квота расходуется быстрее. В худшем случае ответ ждёт `guard.classifier_timeout_seconds` + `llm.timeout_seconds` + `guard.classifier_timeout_seconds`, по умолчанию 10 + 25 + 10 = 45 секунд. Отключить защиту: `APP_GUARD__ENABLED=false`.

**Отдельный классификатор.** Можно задать более дешёвую модель: `guard.classifier_model` (по умолчанию `llm.model`), и даже отдельный OpenAI-совместимый API: `guard.classifier_base_url` (правила те же, что у `llm.base_url`: HTTPS, кроме loopback). Если этот адрес на другом хосте, нужен свой ключ `CLASSIFIER_API_KEY`, иначе приложение не запустится: основной ключ никогда не уходит на чужой хост. Классификатор всегда работает через отдельный HTTP-клиент.

**Модели с рассуждениями.** Рассуждения расходуют `max_tokens` до ответа. Если лимит кончился раньше, ответ приходит пустым (`finish_reason: length`): для классификатора это «нет вердикта», то есть отказ, для основной модели — ошибка `502`. Обрезанный, но непустой ответ сохраняется с пометкой «…(ответ обрезан)» на языке вопроса (ru, en, de, uk, zh, es, fr, для остальных — по-английски); незакрытый блок кода перед пометкой закрывается, в лог пишется предупреждение. Поэтому по умолчанию `guard.classifier_max_tokens` = 1024 (до 4096), а `llm.max_output_tokens` = 4096 (до 8192); с меньшими лимитами классификатор у таких моделей может отказывать на обычные вопросы.

**extra_body.** Провайдер-специфичные поля задаются без правки кода: `guard.classifier_extra_body` добавляется в запрос классификатора, `llm.extra_body` — в запрос основной модели (поля `model`, `messages`, `max_tokens`, `stream`, `response_format` переопределить нельзя; значения должны быть JSON-совместимыми, иначе приложение не запустится). Для вызовов классификатора `guard.classifier_extra_body` заменяет `llm.extra_body`, а не дополняет его. Параметры, которые сокращают рассуждения, провайдеры понимают по-разному и не всегда соблюдают: структурированный ответ надёжнее. Пример:

```yaml
guard:
  classifier_extra_body:
    reasoning_effort: none   # или low; допустимые значения смотрите в документации провайдера
```

В переменной окружения значение задаётся JSON-объектом: `APP_GUARD__CLASSIFIER_EXTRA_BODY='{"reasoning_effort": "low"}'`.

**Качество.** Оно целиком зависит от модели классификатора: слабая модель пропустит атаку или откажет на обычный вопрос. Прежде чем полагаться на защиту с новым провайдером или моделью, прогоните `tests/llm_eval` против настоящего API (см. [Тесты](#тесты)).

## API: подробности

Ошибки всегда имеют вид `{"error": {"code": "..."}}`. Ответы `/api/*` отдаются с `Cache-Control: no-store`. Запросы `POST` и `DELETE` требуют заголовок `Origin` (браузер добавляет его сам).

`GET /api/messages` возвращает последние `limit` записей (по умолчанию 50, максимум 100) в порядке показа: время вопроса, затем `turn_id`. С `before=<turn_id>` — записи, которые идут перед указанной. С `after_revision=<n>` — все записи, сохранённые после этой ревизии, по возрастанию `revision`; в ответе `revision` — курсор для следующего опроса (при первой загрузке — последняя ревизия на момент запроса). `has_more` показывает, есть ли ещё записи. `before` и `after_revision` вместе не принимаются. У каждого сообщения есть `status` (`answered` или `failed`) и `question_at`; у неотвеченной записи нет сообщения ассистента.

| Код ошибки | Статус | Когда |
|---|---|---|
| `unauthorized` | 401 | Нет сессии, сессия истекла или ключ неверный |
| `origin_not_allowed` | 403 | `Origin` отсутствует или не совпадает с адресом сайта |
| `invalid_message`, `invalid_request` | 422 | Сообщение или параметры вне допустимого |
| `too_many_requests` | 429 | Лимит входа или сообщений; смотрите `Retry-After` |
| `model_unavailable` | 502 | Модель вернула ошибку или непригодный ответ |
| `service_unavailable` | 503 | Сервис ещё не готов или недоступна БД |
| `model_timeout` | 504 | Модель не ответила за `llm.timeout_seconds` или классификатор темы — за `guard.classifier_timeout_seconds` |
| `internal_error` | 500 | Непредвиденная ошибка; подробности только в логе |

## Логи

В лог попадают класс ошибки, HTTP-статус и тип ошибки провайдера. Ключ API, заголовки запросов и тексты сообщений в лог не пишутся. Необработанные исключения перехватывает внешний слой приложения: он отвечает `500` и пишет одну запись в лог. Для ошибок БД это только класс, SQLSTATE и имя ограничения, без текста и трассировки, потому что текст ошибки PostgreSQL может цитировать содержимое строк. Исключение дальше не пробрасывается, так что uvicorn не печатает его повторно.

## Тесты

Нужен отдельный тестовый PostgreSQL с правом `CREATEDB`; ключ провайдера не нужен, модель в тестах заменена заглушкой.

```sh
docker run --rm -d --name themed-chat-test-db -e POSTGRES_PASSWORD=test-only -p 127.0.0.1:55432:5432 postgres:17-alpine
docker exec themed-chat-test-db pg_isready -h 127.0.0.1 -U postgres  # повторите, пока не ответит accepting
export TEST_POSTGRES_URL='postgresql+asyncpg://postgres:test-only@127.0.0.1:55432/postgres?ssl=disable'
make check   # lock, Ruff, mypy, unit- и интеграционные тесты
uv run --locked --group browser playwright install chromium && make e2e
docker stop themed-chat-test-db
```

Атаки на настоящую модель проверяет необязательный набор `tests/llm_eval`, он не входит в `make check` и CI:

```sh
APP_LLM__BASE_URL=... APP_LLM__MODEL=... LLM_API_KEY=... uv run pytest tests/llm_eval -m llm_eval -s
```

Без явно заданных `APP_LLM__BASE_URL` и `APP_LLM__MODEL` набор не запускается, чтобы ключ не ушёл провайдеру из YAML по умолчанию. Конфигурацию он читает так же, как приложение (YAML и `APP_*`), и печатает хост и модель, к которым обращается.
